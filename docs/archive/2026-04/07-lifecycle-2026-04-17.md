## Findings

### F-07-1 — No readiness probe for dependency reachability

**Severity:** HIGH · **Location:** `src/server/routes/health.ts`
· **Effort:** S

Same as Audit 03 F-03-1, re-raised here because it's a lifecycle
concern: PM2's healthcheck hits `/health`, which always returns
`{status: "ok"}` as long as the event loop is alive. If Postgres dies,
PM2 keeps the process marked healthy and won't restart it.

**Recommendation**: add `/ready` that runs `SELECT 1` against
Postgres with a 2s timeout and returns 503 on failure. Point
PM2 + the load balancer (when added) at `/ready`. Keep `/health` as
the cheap always-OK liveness probe.

### F-07-2 — Opensky worker loaded asynchronously after `app.listen`

**Severity:** HIGH · **Location:** `src/server/index.ts:113-120` · **Effort:** S

```ts
const server = app.listen(PORT, "0.0.0.0", () => {
  console.log(`[dumont] Server running on port ${PORT}`);
});

if (process.env.ENABLE_OPENSKY !== "false") {
  setTimeout(() => {
    import("../ingestion/opensky-worker.js")
      .then((m) => m.startWorker?.())
      .catch((err) => log.warn({ err }, "opensky worker failed to start"));
  }, 5000);
}
```

Two issues:
1. **`setTimeout(5000)` before worker start** — arbitrary delay, no
   strong guarantee the DB is initialized by then. In practice PG is
   lazy-connected on first query, so this is probably fine, but the
   timing is unspecified.
2. **Failure is silenced** — if the worker fails to start, the API
   stays up and nothing pages. Error lands in `log.warn` (not `.error`),
   so it doesn't flow through to Sentry either.

**Recommendation**: await `startWorker()` inside `server.listen`
callback (after DB is definitely initialized), and log the failure at
`error` so it actually hits Sentry. If the design is "API should serve
even without the worker", keep the current shape but promote the
failure to `log.error` so it's visible.

### F-07-3 — Opensky worker has NO shutdown cleanup path from inside the server

**Severity:** MODERATE · **Location:** `src/server/index.ts:122-138`
· **Effort:** S

The server's `shutdown()` closes DB + PG but does NOT call the stop
function returned from `m.startWorker()`. That means:
- Timer intervals (poll, cleanup, faa-refresh) keep running until
  process exit
- If SIGTERM is slow to propagate (5s grace in `shutdown()`'s
  `setTimeout`), the in-flight poll cycle's bulk write could still be
  executing against a closing PG pool

**Recommendation**: capture the `stop` function when the dynamic
import resolves and call it inside `shutdown()`. Small refactor, ~10
lines.

### F-07-4 — Adsb-feed worker's shutdown calls `closePg()` unconditionally

**Severity:** MODERATE · **Location:**
`src/ingestion/adsblol-live-worker.ts:533` · **Effort:** S

```ts
return async () => {
  console.log("[adsb.lol] Stopping worker...");
  if (pollTimer) clearInterval(pollTimer);
  // ...
  await closePg();
};
```

When this worker is embedded in the API process (it's only started
standalone today, but the pattern mirrors opensky-worker), calling
`closePg()` would tear down the shared pool and break any other
in-flight queries.

**Recommendation**: expose `stopWorker()` as "stop timers", not "close
the pool". Let the caller (standalone entry point vs server embed)
decide whether to close the pool. Same change applies to
`opensky-worker.ts`.

### F-07-6 — Server shutdown has a 5s forced-exit escape hatch

**Severity:** — · **Location:** `src/server/index.ts:130-134`

```ts
setTimeout(() => {
  closeDb();
  if (process.env.DATABASE_TYPE === "postgres") closePg().catch(() => {});
  process.exit(1);
}, 5000).unref();
```

If connections don't drain in 5s, the process force-exits. Good —
prevents PM2 hung-restart loops. `.unref()` means this timer doesn't
itself keep the event loop alive if everything else cleaned up
normally.

### F-07-7 — Bootstrap order is correct

**Severity:** — · n/a

`src/server/index.ts` flow:
1. Imports (side-effect: `initSentry()`, `childLogger` setup)
2. Env validation (warns on missing `ANTHROPIC_API_KEY`, `VAPI_SECRET`)
3. Express app creation
4. CORS, JSON body parser, rate limiters mounted
5. Routers mounted (conversation, health, vapi, deals, chat, radar,
   intelligence, analytics, errorRouter, dashboard)
6. Error middleware mounted LAST (correct Express pattern)
7. `app.listen`
8. (deferred 5s) OpenSky worker start

DB bridge is lazy — PG pool connects on first query. No "routes
served before DB ready" risk because the pool is always available;
first query blocks briefly on connection. ✓

### F-07-8 — No Docker / Kubernetes manifests

**Severity:** LOW · **Location:** `Dockerfile` (obsolete, per
Cleanup Audit F-03) · **Effort:** n/a

Deploy is PM2 on Lightsail, no container orchestration. Liveness /
readiness probes are a PM2-level concern (cwatch config), not k8s
manifests. The skill's probe rule applies with lower severity for
bare-metal deployments.

If we later move to ECS / k8s, the `/health` + `/ready` split from
F-07-1 is what we'd point the probes at.

### F-07-9 — SIGHUP not handled (intentional)

**Severity:** INFORMATIONAL

None of the entry points respond to SIGHUP. For PM2 deployments this
is fine — PM2 uses SIGTERM for graceful reload. If we later want
config reload without restart, add a SIGHUP handler that re-reads
feature flags / LOG_LEVEL.
